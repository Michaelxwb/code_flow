# code-flow 0.8 基线报告

> TASK-001 产物  
> 日期: 2026-10-22  
> 目的: 在改状态机/执行引擎前，把 0.7 的规模与行为固定下来。

---

## 1. 基准 fixture

`tests/test_cf_workflow_scale.py` 构造一个合成需求：

| 维度 | 数量 |
|---|---:|
| TASK | 119 |
| 验收场景 | 190 |
| E2E 场景 | 62 |
| E2E 唯一命令 | 7 |
| Spec binding | 20 |
| 每规则 evidence | 122 |

E2E 命令分布：15 / 14 / 11 / 10 / 4 / 4 / 4，对应现场“同一命令挂多个场景”的形态。

---

## 2. 实测结果

在本机（macOS，Python 3.12）运行 `baseline_metrics()`：

```json
{
  "task_count": 119,
  "scenario_count": 190,
  "e2e_count": 62,
  "unique_e2e_commands": 7,
  "first_decision": "pass",
  "first_executions": 7,
  "first_seconds": 0.135,
  "second_after_unrelated_change_seconds": 0.144,
  "second_executions": 7,
  "second_decision": "pass",
  "context_bytes": 2095389,
  "context_evidence_entries": 2440
}
```

说明：

- `first_executions = 7`：单次运行内，同一命令会被 `run_manifest` 去重。
- `second_executions = 7`：修改一个无关的 tracked 文件后，全局 worktree 指纹失效，7 条 E2E 全部重跑。
- `context_bytes ≈ 2.1 MB`：122 条/规则 × 20 规则 = 2440 条 evidence；现场真实样本为 1.65 MB / 2562 条（规则数与摘要长度不同）。
- `first_seconds` 很小，是因为合成命令只做文件追加；真实 E2E 的耗时在单场景 46s–3min 量级。

## 3. 0.7 行为基线

| 行为 | 0.7 现状 | 0.8 目标 |
|---|---|---|
| 同一命令多场景 | 单次运行内去重，执行 1 次 | 保持 |
| 无关文件改动 | 7 条 E2E 全部重跑 | 0 条重跑 |
| 中断 | 已完成场景不落证据，重跑从 0 开始 | 从下一个 check 继续 |
| context | 每规则追加 evidence，2.1 MB 量级 | <100 KB |
| 场景状态 | 一条命令结果覆盖多个场景 | check 结果 + scenario 断言映射 |
| 并行 worktree | 证据 union 会膨胀，E2E 可能抢环境 | central evidence + batch smoke |

中断基线由 `test_baseline_interrupt_loses_progress` 固定：执行 3 条后中断，manifest 仍全部 `planned`；恢复后 7 条全部重跑。

---

## 4. 复现方式

```bash
python3 -m pytest -q tests/test_cf_workflow_scale.py
```

该测试只保证 fixture 可重复、命令级去重可测量、context 规模可测量；不会把“无关改动全量重跑”断言成永久期望。后续 TASK-004/007/010 会在同一 fixture 上替换为新的期望值。
