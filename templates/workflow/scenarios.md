# {需求名} 验收场景

> 这是给**人工测试者**使用的验收清单，不是 E2E 代码或测试注册表。
> 每个场景保留 S-/E-/B- 编号，供 design 和 Task 的 `Scenarios` 字段引用。
> 步骤用用户能执行的界面动作、CLI 命令或 API 请求描述；期望写用户可观察的结果，避免选择器和内部实现细节。

## S-01 正常完成主流程

- **负责**：TASK-001
- **前置**：
  - 准备可复现的测试数据
  - 服务已启动，测试账号可登录
- **步骤**：
  1. 打开用户实际使用的入口。
  2. 按主流程完成一次操作。
  3. 查看结果页或接口返回。
- **期望**：
  - 操作成功，页面/命令给出明确成功反馈。
  - 关键数据已写入，刷新后仍可见。
- **实际结果**：待执行（通过/失败 + 实际观察）

## E-01 关键依赖失败时明确报错

- **负责**：TASK-001
- **前置**：
  - 已准备一个不可达的外部依赖或错误凭据
- **步骤**：
  1. 触发依赖调用。
  2. 观察错误提示和页面状态。
- **期望**：
  - 用户能看到明确错误，不出现未处理异常或空白页。
  - 不产生部分写入或伪成功。
- **实际结果**：待执行

## B-01 边界输入保持稳定

- **负责**：TASK-002
- **前置**：
  - 已确认字段的长度、数量和格式限制
- **步骤**：
  1. 输入空值、最大长度或临界数量。
  2. 提交并观察结果。
- **期望**：
  - 合法边界被接受，超限输入被明确拒绝。
  - 错误信息能指出需要修改的字段。
- **实际结果**：待执行

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤编号从 1 开始，按真实操作顺序编写。
- 期望写“用户看到什么/数据变成什么”，不要写内部函数名或测试断言。
- 场景不生成 manifest、不登记执行结果、不阻断 `task finish` 或 `task archive`。
- 需要机器执行的快速回归放在 Task 的 `### Tests`；E2E 和全量回归留在 CI。
